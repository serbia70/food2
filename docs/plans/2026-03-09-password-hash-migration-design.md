# Password Hash Migration Design

## 背景

当前后端多个登录口仍使用明文密码存储与明文比对，包括：

- 店铺后台登录
- 主控登录
- 骑手注册/登录
- 用户注册/历史登录

这会带来明显的安全风险：数据库泄露即等于口令泄露，且后续无法安全扩展密码策略。

## 目标

在不强制现网用户立刻重置密码的前提下，把所有密码存储逐步迁移到 bcrypt 哈希，并保证现有账号仍可平滑登录。

## 推荐方案

采用“渐进式 bcrypt 迁移”：

1. 新注册、新建账号、改密码一律写入 bcrypt 哈希。
2. 登录校验统一走密码工具层。
3. 对旧明文存量账号，允许一次兼容登录。
4. 明文账号登录成功后，立即原地升级为 bcrypt 哈希。

## 范围

本轮覆盖以下表与流程：

- `master_admin.password`
- `shops.password`
- `riders.password`
- `users.password`

涉及：

- 主控登录与主控改密
- 店铺登录与主控创建/修改店铺密码
- 骑手注册/登录
- 用户注册/历史登录
- 默认主控种子密码

## 设计

### 1. 统一密码工具层

新增密码工具，提供：

- `HashPassword(plain string) (string, error)`
- `VerifyPassword(stored string, plain string) (ok bool, needsUpgrade bool)`
- `LooksLikeBcryptHash(stored string) bool`

职责：

- 统一 bcrypt 成本与错误处理
- 识别旧明文与新哈希
- 返回“是否需要升级”而不是让 handler 自己判断

### 2. 登录兼容与自动升级

各登录口统一流程：

1. 查出数据库里的 `stored password`
2. 调用 `VerifyPassword`
3. 若失败，返回通用 `invalid credentials`
4. 若成功且 `needsUpgrade = true`，则：
   - 生成 bcrypt 哈希
   - 原地写回当前账号密码字段
   - 不影响本次登录成功响应

### 3. 写入侧统一哈希化

以下场景改为只写入哈希：

- 主控初始化种子密码
- 主控改密
- 主控创建店铺 / 更新店铺密码
- 骑手注册
- 用户注册

### 4. 风险控制

- 不改表结构，避免额外迁移风险
- 不做离线全量批量重写，避免误伤未知数据
- 明文兼容窗口只存在于登录校验路径，后续账号一旦成功登录即完成升级
- 所有错误返回继续保持通用文案，不泄露密码格式或校验细节

## 测试

### 单元测试

- 密码工具：哈希、校验、识别 bcrypt、明文兼容判断

### 回归测试

- 主控登录：
  - bcrypt 账号可登录
  - 明文旧账号可登录并被升级
- 店铺登录：
  - bcrypt 账号可登录
  - 明文旧账号可登录并被升级
- 骑手登录/注册：
  - 新注册写入哈希
  - 明文旧账号可登录并被升级
- 用户注册/历史登录：
  - 新注册写入哈希
  - 明文旧账号可登录并被升级

## 部署说明

- 这是向前兼容方案，部署后不需要立刻重置密码
- 建议部署后优先验证：
  - 主控登录
  - 店铺后台登录
  - 骑手登录
  - 用户登录
- 旧账号在首次成功登录后会自动从明文迁移为哈希
