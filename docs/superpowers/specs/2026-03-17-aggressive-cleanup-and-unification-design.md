# 2026-03-17 — 激进清理与统一逻辑（保持功能不变）设计

## 目标
在**保留所有现有功能**（用户点餐、购物车、下单、用户中心、预订、聊天/MQTT、admin 后台、master 等）的前提下，对项目做“激进但可控”的清理与统一：

- 删除无效/死代码与无入口文件（可证明未使用的）
- 去重复：把散落的同类逻辑收敛到少数权威实现（single source of truth）
- 统一边界与模式：同类 API route / 脚本 / 组件遵循同一套规则
- 降低维护成本：减少“改一处、另一个角落坏掉”的概率

## 非目标（本轮不做）
- 不做 UI 换皮/设计风格大改（除非是为了解耦 CSS、去重复）
- 不引入新的运行时依赖（保持轻便）
- 不追求把所有东西一次性完美重写（每批可回滚、可验证优先）

## 约束与安全护栏
### 功能约束
- **功能都要保留**：允许重构实现，但不允许砍模块。
- 不改对外路由路径与对外 API 形状（除非本来就是 bug）。
- 不改已有存储 key（localStorage/cookie）与数据契约（除非明确纳入某批改动并加回归用例）。

### 运行环境约束
- Astro + Cloudflare Pages/Workers：运行时代码避免 Node-only API。
- iOS 12 兼容：避免现代语法/新 API（由现有 build target + compat + security gate 约束）。

### 每一批都必须执行的验证（硬门禁）
每个 Batch 完成后，必须 fresh 跑完并通过：

1. `pnpm build`
2. `pnpm run test:security`
3. 相关的额外用例（该批涉及到的单测/脚本，按需增加）

若任何一项失败：停止进入下一批，先修复或回滚该批。

### 回滚策略
- 每个 Batch 独立 commit（小步提交）
- 如果某批引入不稳定，可直接回退到上一批 commit

## 回归验证清单（每个 Batch 必跑）
> 自动门禁（build + security tests）能挡住大类问题，但不等价于“功能不变”。每批都要做一遍轻量手工 smoke。

### 用户侧（点餐核心）
- 打开店铺页：分类/商品列表正常渲染；图片能显示（或至少不会阻塞交互）
- 加购：加入购物车、修改数量、删除
- 购物车弹窗：能打开/关闭；不会被底栏遮挡；结算按钮可点
- 下单流程：进入下单页（成功/失败均不应白屏）
- 用户中心：打开/关闭；登录/注册入口可用；历史订单列表可渲染

### 预订与聊天
- 预订入口可见且双语文本保留（“预订” + “Rezervacija”）
- 聊天入口可打开（MQTT 是否可用取决于环境，但 UI 与降级表现必须可用）

### Admin 后台
- admin 登录页可用；登录后点击按钮/切 tab 不应失效
- 订单列表/桌台/菜单/设置：至少打开一次，确认无 JS 报错导致核心交互失效

### Master
- master 入口页面至少可打开、能渲染主要卡片（不要求真实数据）

## 删除规则（“可证明未使用”的定义）
删除文件/导出必须满足以下原则，否则默认不删：

- **引用证据**：在仓库内不存在静态引用（import/require/路径引用/URL 引用）。
  - 注意：通过 `window.xxx`、data-attribute、querySelector、字符串拼接路径等隐式耦合，必须先定位调用方再决定。
- **构建证据**：`pnpm build` 通过；且删除不应导致运行时路由缺失/构建失败。
- **行为证据**：按本 spec 的“回归验证清单”跑完，关键流程无回退。

每次删除必须在 commit message 或 PR 描述里写一句“删除依据/证据摘要”（例如：全仓无引用 + build 通过 + smoke 通过）。

## Preflight（盘点，不改行为）
在开始 Batch A 前，先完成一次最小盘点（不改逻辑，只记录）：
- API routes 清单：`src/pages/api/**` 下按“需要 auth / 是否 JSON / 是否上传/文件类”分组。
- 关键入口清单：用户点餐/用户中心/预订/聊天/admin/master 的入口页面路径与触发点。

## 工作分解（分批执行）
> 目标是“每批只解决一类问题”，并在批间形成稳定基线。

### Batch A — 统一 API 边界（proxy/auth/json/cache）
**问题特征**：大量 API routes 重复实现：
- 读取 `authorization` header 与 `admin_token` cookie
- `no-store`/cache headers
- JSON parse 容错与错误包装

**做法**：
- 优先复用 `src/lib/api-proxy.ts`、`src/lib/admin-api-route.ts` 等现有能力
- 将散落的重复实现收敛为少量共享 helper
- 逐个替换 routes 中重复逻辑，避免“某个 route 漏改”

**风险边界（必须保持不变，除非在本批明确列入“允许变化清单”并补回归）**：
- HTTP status code：上游返回什么就返回什么（仅在明确的“包装错误”策略中例外）
- Headers：尤其是 `Content-Type`、`Cache-Control`、`Pragma`、`Set-Cookie` 行为
- Body 语义：
  - JSON endpoint：保持 JSON 透传/错误包装策略一致
  - 非 JSON endpoint（文件/图片/纯文本）：不得强行包成 JSON
- 超时/连接中断：错误码与错误 JSON schema 不随意改动（避免前端依赖字段崩溃）

**验收**：
- 所有现有 admin API route 行为不变（status/headers/body 语义不回退）
- 代码重复显著下降（同类 auth/proxy 逻辑只剩 1 个权威实现）

### Batch B — 拆 admin 大页（src/pages/admin/[slug]/index.astro）
**问题特征**：页面内联工具函数/业务拼装过多，导致：
- 难读、难测、易出现重复实现
- 修改风险集中在单个大文件

**做法**：
- 把纯逻辑（parse/normalize/date/table-cards 等）抽到 `src/lib/admin/*` 或现有 lib 目录
- 页面只保留：数据获取 + 数据清洗调用 + 组件渲染

**验收**：
- 页面功能不变（登录态校验、各 tab、订单/桌台/菜单等）
- 页面文件显著瘦身，可读性提升
- 新抽离逻辑有对应的单元测试或被现有测试覆盖

### Batch C — 拆用户中心（UserModal/UserCenterPanel 体系）
**问题特征**：用户中心相关组件体量大、混合 UI 与状态逻辑，存在不稳定写法风险点。

**做法**：
- 以“职责拆分”为主：登录/注册、地址摘要、订单列表、资料编辑、底部结算栏等拆成小组件/小模块
- 清理明显不稳定/不可复现写法（例如随机 id）
- 统一事件与状态流（继续遵循现有事件常量与 store）

**验收**：
- 登录/注册、历史订单、编辑资料、去结算、聊天联动等均保持可用
- 代码结构可测试、可替换，不再依赖“大文件硬堆”

### Batch D — CSS 结构化（global.css/admin-global.css）
**问题特征**：全局 CSS 超大、重复与覆盖关系隐蔽。

**做法**：
- 不做视觉重设计，只做：分区、去重复、减少互相覆盖
- 将明显模块（底栏、modal、页面布局、表单、badge 等）组织成稳定段落（或拆分为少数文件并由 Layout 引入）

**验收**：
- 视觉不出现明显回退（底栏/弹窗/主要页面布局一致）
- 同类样式只保留一处权威定义，减少重复覆盖

## Stop Conditions（必须停下来对齐的情况）
- 单个 Batch 需要改动超过 10+ 文件且难以解释“为何必须一起改”
- 验证门禁失败且连续 2 次无法在该批内修复
- 发现功能行为确实无法保持（需要产品级决策）
- 任何改动需要后端 API 契约配合，或需要新增/改变 Cloudflare 环境变量语义（必须停下来单独对齐/另起 spec）

## Definition of Done（本轮完成标准）
- 所有 Batch 按顺序完成，每批验证均通过
- 主要热点大文件拆分或显著瘦身，重复逻辑收敛
- 安全门禁测试持续通过（无 unsafe DOM sinks、无 secrets、兼容性 gates 通过）
