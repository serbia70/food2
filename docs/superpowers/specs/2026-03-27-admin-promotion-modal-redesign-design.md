# Admin 促销弹窗重设计 Design

**Goal:** 重做 `/admin/[slug]` 营销页里的“添加/编辑促销”弹窗，重点优化“今日特价”选菜区域的可读性、选择效率和响应式宽度。

**Why:** 用户明确反馈当前促销弹窗“很丑”，特别是今日特价的菜品选择区域过窄、信息拆成两行、没有中文菜名、没有搜索能力，导致选菜慢且容易看错。此次设计只解决促销弹窗交互和排版，不扩展新的促销类型，也不改后端促销规则。

## Scope

本次只调整 admin 促销弹窗的前端结构与交互：

- 重做 `promotion-modal` 的宽度与内部布局
- 重做 `promo_type === 'special'` 时的菜品选择区
- 增加菜品搜索框
- 展示中文名 + 外文名 + 价格的单行菜品信息
- 增加已选菜品区，使用标签式多选交互
- 保持创建与编辑促销共用同一弹窗
- 保持现有促销提交接口与 payload 字段不变
- 保持 `selected_products` 仍提交为产品 id 数组
- 不新增拼音搜索
- 不新增新的促销类型
- 不改促销列表页卡片结构
- 不改后端 `/api/admin/promotions` 系列接口

## Current Problems

### 1. 弹窗过窄

当前 `src/components/admin/TabMarketing.astro` 中 `promotion-modal` 内容容器固定为 `max-width: 500px; width: 90%`，对于包含多个字段和多选列表的表单明显过窄，桌面端信息密度太高，阅读与选择都不顺手。

### 2. 今日特价选菜区只有滚动勾选列表

当前 special 模式下只有一个 `#promo-product-list` 容器，里面按 checkbox 纵向堆叠菜品，已选和待选混在一起，用户需要反复滚动查找，无法快速确认自己已经选了哪些菜。

### 3. 菜品信息维度不够

当前 `loadProducts()` 仅保留 `{ id, name, price }`，渲染时只展示一个 `name` 和价格，无法同时显示中文名与外文名，也没有清晰的回退规则。

### 4. 缺少搜索

菜品多时，当前只能肉眼滚动寻找目标菜，效率很差。

## Design

### 1. 弹窗整体改为中等偏宽，并保持移动端自适应

`promotion-modal` 内容容器改为中等偏宽的桌面布局，目标宽度约 900px，不再使用当前 500px 窄弹窗。

推荐行为：

- 桌面端：`width: min(900px, calc(100vw - 48px))`
- 小屏端：自动收缩到 `calc(100vw - 24px)` 左右，避免贴边
- 保留 `max-height: 90vh` 与内部滚动
- 表单基础字段改成更稳定的两段式布局，而不是所有字段一列到底

这样桌面端能容纳“基础信息 + 时间区 + 今日特价选择器”，移动端仍能自然回落成单列。

### 2. 仅重做 special 类型的选菜区，其他促销类型保持轻量

`spend_discount`、`percent_discount`、`bonus_points` 三类促销仍保持现有简单字段结构，本次重构聚焦 `promo_type === 'special'`。

当类型切换为 `special` 时，展示一个新的三段式选菜区：

1. 搜索栏
2. 已选菜品区
3. 待选菜品列表

当类型不是 `special` 时，这整块区域继续隐藏，不影响现有其他促销流程。

### 3. special 选菜区采用“搜索 + 已选标签 + 待选列表”的结构

#### 3.1 搜索栏

在选菜区顶部增加一个搜索输入框，仅用于过滤待选菜品列表。搜索规则：

- 支持中文名包含匹配
- 支持外文名包含匹配
- 不做拼音匹配
- 不按价格搜索
- 输入为空时显示全部待选菜品

搜索是纯前端过滤，不改接口。

#### 3.2 已选菜品区

已选菜品单独展示在搜索框下方，使用标签/卡片式小块展示，每个已选项至少包含：

- 中文主名（优先）
- 外文副名（有则显示）
- 价格
- 移除按钮

作用：

- 用户一眼能确认当前已选内容
- 不需要回到长列表里反复找勾选状态
- 编辑促销时可以直接看到回填结果

#### 3.3 待选菜品列表

待选区域只展示“未被选中且符合搜索条件”的菜品。每行固定为单行信息布局，不再拆成两行。

每行内容顺序：

- 中文名（主视觉）
- 外文名（次级灰字，无则不显示）
- 价格
- 选择按钮

这样可以满足用户“明明一行就可以显示”的要求，同时保持高密度浏览。

### 4. 中文名 / 外文名展示采用前端回退规则

当前菜单数据里至少能稳定拿到 `name`，且项目其他地方已有 `sub_name` 使用痕迹，因此本次设计采用以下回退规则：

- `primaryName`: `p.name`
- `secondaryName`: `p.sub_name`
- 如果 `sub_name` 为空，则只显示主名，不渲染副名占位
- 如果未来接口只返回单名，也不会阻塞当前 UI

也就是说，本次不引入新的字段协议，只是在前端读取已有可能存在的 `sub_name`，没有就优雅降级。

### 5. 选择交互从 checkbox 列表改为显式增删

special 模式下不再依赖“长列表里的 checkbox 勾选状态 + 单独扫描 DOM”作为主要心智模型，而改为更明确的状态管理：

- 选中某行时，把该菜加入已选区
- 已选区点击移除时，把该菜从已选区移出
- 待选列表不重复显示已选项目
- 提交时仍从当前已选状态生成 `selected_products`

这样交互更接近标签式多选，也更容易保证创建与编辑时的一致回填。

### 6. 编辑促销时必须完整回填 special 选择状态

编辑已有 `special` 促销时：

- 解析 `selected_products`
- 先恢复已选状态
- 再按当前搜索词渲染待选列表
- 已选项不因为搜索条件被隐藏或丢失
- 特价金额仍沿用现有 `special_price_rsd` 回填逻辑

搜索只影响“待选列表展示”，不影响已选集合本身。

### 7. 保持提交 payload 和接口不变，避免扩大改动面

本次仅重构前端交互，不改后端接口约定。提交时仍保持：

- `promo_type === 'special'` 时发送 `selected_products: number[]`
- `special_price_rsd` 继续作为特价金额字段
- 创建走 `POST /api/admin/promotions`
- 编辑走 `PUT /api/admin/promotions/:id`

这样可以把改动收敛在 `TabMarketing.astro` 内，避免引入额外后端联动风险。

## Verification

### 源码回归测试

增加或更新源码断言，至少覆盖：

1. 弹窗宽度不再是 `max-width: 500px`
2. 存在 special 搜索输入区
3. 存在已选菜品区容器
4. 列表渲染包含 `name` 与 `sub_name` / `subName` 的展示逻辑
5. 编辑促销时 special 选中项会回填
6. 搜索过滤逻辑仅作用于待选列表

### 手动检查

1. 打开“添加促销”，弹窗在桌面端明显更宽，移动端不贴边
2. 切换到“今日特价”后出现：搜索框、已选区、待选列表
3. 待选列表单行显示中文名 / 外文名 / 价格 / 选择动作
4. 选择菜品后，项目进入已选区，并从待选列表消失
5. 从已选区移除后，项目重新回到待选列表
6. 输入中文关键字能过滤结果
7. 输入外文关键字也能过滤结果
8. 编辑已有今日特价时，已选菜品和特价金额正确回填
9. 保存后 payload 仍是原接口需要的字段结构
