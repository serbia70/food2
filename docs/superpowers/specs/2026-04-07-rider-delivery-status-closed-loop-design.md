# 骑手配送闭环与多端状态同步设计

## 背景
当前配送链路已经具备以下基础：
- admin 可派单并查看外卖订单；
- rider web 可接单；
- Telegram 可接单 / 拒单；
- 订单主状态已覆盖 `awaiting_courier`、`delivering`、`completed`；
- 拒单反馈已通过 remarks / dispatch meta 持久化。

但实际交互仍存在三类问题：
1. admin、rider web、Telegram、买家侧对同一订单的状态感知不同步；
2. Telegram 拒单反馈与 admin 展示之间仍容易出现延迟感，用户必须刷新才能确认结果；
3. 接单后缺少“已取餐”这一中间真实阶段，导致配送中语义过粗，买家、商家、骑手都无法准确感知配送进展。

用户已明确要求本轮遵守以下原则：
- 优先稳定；
- 多端状态必须同步；
- 能共用接口就共用接口；
- 公共接口必须稳定、干净、无污染；
- 代码保持简洁、轻便、便于后续修改，避免堆叠分叉逻辑。

## 目标
本轮目标是建立一个稳定、统一、最小扩展的配送闭环：

1. 新增真实持久化状态 `picked_up`，形成完整配送状态链；
2. admin、rider web、Telegram、买家侧共用同一套状态真相；
3. rider web 与 Telegram 都支持两个新增动作：
   - 已取餐
   - 已送达
4. admin 也可以对配送中的订单执行相同推进动作；
5. 拒单仍作为辅助反馈而非主状态，继续沿用 remarks / dispatch meta；
6. 统一状态文案、颜色与按钮规则，避免每个入口各写一套业务判断。

## 非目标
本轮不做以下扩散：
- 不新增第二套配送状态系统；
- 不为 Telegram 单独发明一套业务接口；
- 不在公共接口中增加 `fromTelegram`、`uiState`、`surface` 等污染参数；
- 不重做整套 rider 权限模型或消息系统；
- 不顺手重构无关的 master / admin 功能；
- 不把拒单升级为新的订单主状态。

## 核心设计决策
### 1. 引入一个真实新状态：`picked_up`
订单配送主状态统一为：
- `pending`
- `confirmed`
- `awaiting_courier`
- `delivering`
- `picked_up`
- `completed`

其中本轮新增且唯一新增的是：
- `picked_up`：骑手已取餐，正在前往送达。

这是本轮最关键的结构化改动。它解决的问题是：
- `delivering` 只表示“骑手已接单”；
- `picked_up` 表示“已经取到餐并在送达途中”；
- `completed` 表示“已送达完成”。

这样买家、商家、骑手都能看到真实的阶段推进，而不是把“接单后到送达前”的所有语义都压缩成一个状态。

### 2. 只保留一条公共状态推进链
所有端都复用现有订单状态更新能力，不新开平行接口。

统一状态推进：
- `awaiting_courier -> delivering`
- `delivering -> picked_up`
- `picked_up -> completed`

统一原则：
- 哪个端触发动作不重要；
- 订单推进到什么状态才重要；
- 业务真相只能由后端订单状态决定。

也就是说：
- Telegram 的“已取餐”按钮；
- rider web 的“已取餐”按钮；
- admin 的“标记已取餐”按钮；

都应打到同一条后端状态更新链，只是目标状态相同。

### 3. 拒单继续作为辅助反馈，不污染主状态机
“暂不接单 / 拒单”继续保留现有语义：
- 订单主状态仍保持 `awaiting_courier`；
- remarks / dispatch meta 记录：
  - `lastRiderDecision`
  - `declinedRiderIds`
  - 相关失效骑手信息

这样做的理由：
- 拒单不是订单生命周期的主阶段；
- 它只是当前骑手对这单的反馈；
- 若把拒单做成主状态，反而会污染稳定的配送状态链。

## 统一状态机
### 主状态定义
#### `awaiting_courier`
- 含义：订单正等待骑手确认；
- 可执行动作：接单、暂不接单；
- admin 可见反馈：最近一次骑手拒单信息（若有）。

#### `delivering`
- 含义：骑手已接单，尚未确认取餐；
- 可执行动作：已取餐；
- 买家侧文案：送餐中。

#### `picked_up`
- 含义：骑手已取餐，正在送达途中；
- 可执行动作：已送达；
- 买家侧文案：骑手已取餐，正在送达。

#### `completed`
- 含义：订单已送达完成；
- 不再显示活跃配送动作。

### 状态转换
- 接单：`awaiting_courier -> delivering`
- 已取餐：`delivering -> picked_up`
- 已送达：`picked_up -> completed`
- 暂不接单：保持 `awaiting_courier`，只写拒单反馈

### 并发与幂等要求
后端必须继续作为唯一状态守门人：
- 重复点击旧按钮不能产生脏写；
- 已被其他骑手接走的单，再点“接单”应返回状态不匹配；
- 已推进到 `picked_up` 的订单不能再接受 `delivering` 动作；
- 已完成订单不能再次推进；
- Telegram、rider web、admin 的旧页面按钮都只能得到明确失败，而不能把状态写乱。

## 多端行为设计
### admin
admin 负责管理视角与兜底推进能力。

#### 列表展示
在 `TabTables.astro` 外卖区：
- `awaiting_courier`：显示“待骑手确认”或“待骑手接单”；若最近一次决策为拒单，则显示“骑手已拒单”辅助反馈；
- `delivering`：显示“骑手已接单”；
- `picked_up`：显示“骑手已取餐”；
- `completed`：显示“已送达”或维持既有完成语义。

#### 颜色
- `delivering` / 骑手已接单：蓝色或绿色高可见标签；
- `picked_up`：绿色推进态；
- 拒单反馈：红色；
- 不再混用模糊灰色文案让人靠猜判断。

#### 按钮
- `awaiting_courier`：保留现有指派 / 自动派单 / 结账 / 拒绝等；
- `delivering`：增加“已取餐”；
- `picked_up`：增加“已送达”；
- `completed`：不再显示配送推进动作。

admin 的推进按钮和 rider / Telegram 一样，全部复用同一状态更新能力。

### rider web
rider dashboard 是骑手主动操作面。

#### `awaiting_courier`
显示：
- 接单
- 暂不接单

#### `delivering`
显示：
- 已取餐

#### `picked_up`
显示：
- 已送达

#### 原则
- 一个状态只显示当前阶段该做的动作；
- 不在同一卡片放多个冲突主动作；
- rider web 不单独维护业务状态，只消费共享规则。

### Telegram
Telegram 是另一种 UI，不是第二套业务系统。

#### 阶段 1：待接单消息
按钮：
- 接单
- 暂不接单

接单成功后：
- 调用同一条状态更新链，把订单推进到 `delivering`；
- 成功后再发送下一阶段消息，按钮为“已取餐”。

#### 阶段 2：已接单 / 待取餐消息
按钮：
- 已取餐

点击后：
- 调用同一条状态更新链，把订单推进到 `picked_up`；
- 成功后再发送下一阶段消息，按钮为“已送达”。

#### 阶段 3：已取餐 / 待送达消息
按钮：
- 已送达

点击后：
- 调用同一条状态更新链，把订单推进到 `completed`。

#### 设计原则
Telegram 采用“阶段推进消息”而不是在一条旧消息上塞完所有状态分支，理由是：
1. 更稳；
2. 旧按钮失效更容易处理；
3. 状态含义更直观；
4. 不需要复杂编辑旧消息逻辑。

### 买家侧
买家侧只读真实订单状态，不认 Telegram 或 rider 的临时动作。

文案统一：
- `delivering`：送餐中
- `picked_up`：骑手已取餐，正在送达
- `completed`：已送达

买家侧不新增额外动作，只做稳定展示。

## 接口设计原则
### 公共接口必须稳定、干净
本轮明确禁止：
- 为 Telegram 单独新增并行配送接口；
- 在公共状态更新接口里混入端侧专用字段；
- 为某一个页面临时加脏兼容参数。

公共接口应只接受真正的业务输入，例如：
- 订单 id
- 目标状态
- 当前预期状态
- 骑手姓名 / 电话（在原本就需要的地方）

不能接受的污染式设计示例：
- `surface: 'telegram'`
- `fromAdmin: true`
- `uiState: 'picked_up_card'`
- `skipValidation: true`

### 单一事实来源
所有端最终以订单真实状态为准：
- 后端持久化状态是唯一真相；
- 前端和 Telegram 只负责发动作、读结果；
- 不允许本地先改 UI 假装成功，再等待慢同步修正。

## 共享逻辑设计
本轮应把以下规则收口到共享层，而不是散落在多个页面：
1. 状态中文文案映射；
2. 状态颜色映射；
3. 不同状态可执行动作映射；
4. 拒单辅助反馈文案生成。

admin、rider web、买家侧都消费同一映射规则。

这样可避免：
- `TabTables.astro` 一套 if/else；
- `rider/dashboard.astro` 再写一套；
- Telegram callback 再写第三套；
- 后续改文案或新增状态时改三四遍。

## 文件边界

- `foos2Go/internal/handlers/order_update_status*.go`
  - 扩状态跃迁规则；
  - 校验合法性；
  - 保持接口稳定。

- `foos2Go/internal/handlers/order_list_flow.go`
  - 保证列表回包里能稳定透出 `picked_up`；
  - 不做端侧污染式拼装。

### 前端共享层
- `src/lib/rider-dispatch.ts`
- `src/lib/telegram-dispatch.ts`
- 如有必要，可新增一个最小共享 helper（例如配送状态文案 / 动作规则），但前提是真正减少重复。

### admin
- `src/components/admin/TabTables.astro`
  - 显示统一状态；
  - 新增“已取餐 / 已送达”推进按钮；
  - 收敛颜色语义。

### rider
- `src/pages/rider/dashboard.astro`
  - 按共享规则显示按钮；
  - `delivering` 阶段显示“已取餐”；
  - `picked_up` 阶段显示“已送达”。

### Telegram
- `src/pages/api/telegram/rider-claim.ts`
  - 保留接单 / 拒单入口；
  - 接单成功后推进到下一阶段消息。

- 现有 Telegram callback 链路上最小扩展：
  - `picked_up` 按钮处理
  - `completed` 按钮处理

不新造第二套并行入口体系。

## 错误处理
### 目标
错误处理只做必要部分，重点是稳定和真实，不做臃肿兜底。

### 规则
1. 非法状态跃迁由后端明确拒绝；
2. 前端 / Telegram 收到失败时展示真实错误，不伪成功；
3. 旧按钮点击失败时给出简短可理解反馈；
4. 刷新后必须能从真实订单状态恢复正确展示；
5. 不依赖内存态修正 UI。

### 不做的事
- 不做本地假推进；
- 不做多层前端缓存状态机；
- 不做只为了某个入口看起来顺滑的特殊分支；
- 不往公共接口中追加一次性兼容字段。

## 测试策略
本轮必须采用 TDD，至少覆盖以下红灯：

### 后端
1. `awaiting_courier -> delivering` 合法；
2. `delivering -> picked_up` 合法；
3. `picked_up -> completed` 合法；
4. 非法跳转被拒绝；
5. 订单列表能透出 `picked_up`；
6. 拒单 remarks 仍能保留并被 admin 正确消费。

### admin
1. `delivering` 显示“骑手已接单”且为蓝/绿；
2. `picked_up` 显示“骑手已取餐”；
3. 有最近拒单反馈时显示红色“骑手已拒单”；
4. `delivering` 阶段出现“已取餐”按钮；
5. `picked_up` 阶段出现“已送达”按钮。

### rider web
1. `awaiting_courier` 显示“接单 / 暂不接单”；
2. `delivering` 显示“已取餐”；
3. `picked_up` 显示“已送达”；
4. 不同状态不会混出错误按钮组合。

### Telegram
1. 待接单消息包含“接单 / 暂不接单”；
2. 接单成功后发送“已取餐”阶段消息；
3. 已取餐成功后发送“已送达”阶段消息；
4. 已送达成功后落库为 `completed`；
5. 旧按钮 / 状态不匹配时返回明确失败。

### 买家侧
1. `delivering` 显示“送餐中”；
2. `picked_up` 显示“骑手已取餐，正在送达”；
3. `completed` 显示“已送达”。

## 风险与控制
### 风险 1：公共接口被越改越脏
控制：
- 明确只复用现有状态更新语义；
- 审查时拒绝加入端侧专用字段；
- 共享规则抽到最小公共层。

### 风险 2：多端文案再度分裂
控制：
- 统一状态文案和颜色映射；
- 页面只消费映射，不各自硬编码。

### 风险 3：Telegram 分阶段消息带来旧按钮问题
控制：
- 依赖后端状态守门；
- 旧按钮只会失败，不会写乱状态；
- 失败回包保持简短明确。

### 风险 4：为了“即时感”引入前端假状态
控制：
- 坚持后端真实落库优先；
- 不做本地伪同步；
- 同步问题优先修真实链路，而不是补视觉假象。

## 验收标准
### 功能验收
1. rider web 与 Telegram 都有“已取餐 / 已送达”；
2. admin 也可推进 `delivering -> picked_up -> completed`；
3. 买家、卖家、骑手都能看到一致的配送进度；
4. 拒单反馈仍可在 admin 中稳定显示。

### 一致性验收
1. 多端使用同一主状态链；
2. 多端推进动作全部复用同一后端状态更新语义；
3. 不存在某一端独有的配送主状态；
4. 公共接口没有新增污染字段。

### 稳定性验收
1. 重复点击不会写坏状态；
2. 旧按钮只能失败，不能脏写；
3. 刷新后页面仍能根据真实状态恢复正确展示；
4. 拒单、接单、已取餐、已送达四类动作都能稳定落库并回显。

## 最终结论
本轮采用以下最终决策：
- 只新增一个真实状态：`picked_up`；
- 维持单一订单主状态机；
- 拒单继续作为辅助反馈，不升级为主状态；
- admin、rider web、Telegram、买家侧共享同一状态真相；
- 所有状态推进动作复用同一后端状态更新链；
- 公共接口保持稳定、干净、无污染；
- 共享文案 / 颜色 / 按钮规则，避免多处重复业务判断。
