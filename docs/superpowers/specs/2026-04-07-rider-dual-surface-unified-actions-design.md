# 骑手端与 Telegram 统一三动作交互设计

## 背景
当前项目同时保留两套骑手执行面：
- `rider dashboard`：适合安装后直接打开操作；
- `Telegram`：用于弥补 WPA 模式在手机关屏时通知不稳定的问题。

因此这不是“二选一”替换，而是同一配送流程的双入口并存。目标是让骑手无论从哪个入口进入，都看到一致的动作语义、状态文案和操作顺序，尽量做到“一看就会”。

另外，当前派单相关文案在 admin、rider、Telegram 多处存在分裂，例如“待骑手确认 / 待骑手接单 / 骑手已接单 / 配送中”混用；rider dashboard 的卡片排版也偏临时拼接，信息层级和按钮主次不清晰，需要同步收敛。

## 目标
本轮要同时实现三件事：

1. 骑手端与 Telegram 都支持三类动作：
   - 接单
   - 暂不接单
   - 送餐完成
2. 两个入口共用同一套状态流与动作语义，不再各走一套
3. rider dashboard 改成简洁商务风，减少信息拥挤和误操作
4. 将派单相关状态文案统一为订单列表语义

## 非目标
本轮不做以下扩散：
- 不重做整套 rider 系统路由或权限模型
- 不把 Telegram 改成复杂的多消息同步编辑系统
- 不新增新的配送业务状态（例如“已到店”“取餐中”）
- 不顺手重构无关 admin / master 功能
- 不改当前“拒单后订单仍停留在待骑手池”的业务语义

## 统一状态机
### 状态定义
配送链路继续围绕现有三态收敛：

- `awaiting_courier`
  - 含义：订单正在等骑手响应
  - 可执行动作：接单、暂不接单
- `delivering`
  - 含义：已有骑手接单并在配送中
  - 可执行动作：送餐完成
- `completed`
  - 含义：配送完成
  - 不再显示动作按钮

### 动作与状态转换
- 接单：`awaiting_courier -> delivering`
- 暂不接单：保持 `awaiting_courier`，但写入当前骑手拒单反馈
- 送餐完成：`delivering -> completed`

### 并发与幂等约束
所有真正改变状态的动作继续以后端为准，沿用现有 `expected_current_status` 约束：
- 多骑手同时抢单时，先成功者生效；后续动作得到“状态已变化”反馈
- 已完成或已被他人接走的旧按钮点击，不应产生脏写
- Telegram 与 rider dashboard 都只是入口，不单独拥有状态真相

## 双端统一动作规则
### Telegram
#### 阶段 1：待接单消息
消息正文只保留骑手决策需要的关键信息：
- 店铺名
- 订单号 / 取餐号
- 地址
- 电话
- 金额
- ETA
- 预约送达（有才显示）
- 商品摘要（保留精简版，超长截断）

按钮：
- `接单`
- `暂不接单`

#### 阶段 2：配送中消息
当骑手接单成功后，系统再发送一条新的配送消息，而不是强依赖更新原消息按钮。

按钮：
- `送餐完成`

采用“新消息推进下一阶段”而非“原消息动态切换”有三个原因：
1. 对 Telegram 来说更稳，不依赖旧消息编辑成功与否；
2. 骑手看到的动作永远只有当前阶段该做的那一个，不会混乱；
3. 更容易处理旧按钮点击、过期按钮、消息不同步。

### rider dashboard
#### 待接单池
只展示 `awaiting_courier` 订单。

按钮：
- 主按钮：`接单`
- 次按钮：`暂不接单`

#### 我的配送
只展示当前骑手自己的 `delivering` 订单。

按钮：
- 主按钮：`送餐完成`
- 次按钮：`联系客户`
- 次按钮：`导航`

#### 历史区
继续只展示已结束订单，不放活跃动作按钮。

### 双端一致性原则
无论从 Telegram 还是 rider dashboard 进入，骑手对同一订单都应遵守同一个认知：
- 等待时只能“接单 / 暂不接单”
- 接单后只能“送餐完成”
- 结束后不再有动作

## 文案统一规范
本轮统一派单相关状态文案，以现有订单列表语义为准：
- `awaiting_courier` -> `待骑手接单`
- `delivering` -> `配送中`
- `completed` -> `已完成`

拒单反馈不是新的主状态，而是辅助说明：
- 例如：`骑手反馈：张三已拒单 12:36`

这类反馈可以显示在 admin 与 rider 需要的场景中，但不能替代主状态机，避免把“拒单反馈”和“订单业务状态”混为一体。

## rider dashboard 视觉改造
### 风格目标
采用“简洁商务风”：
- 白底卡片
- 清晰分层
- 稳定、克制、易扫读
- 主操作突出，次操作弱化

不做偏娱乐化、过度鲜艳、科技炫技风格。

### 页面结构
页面保留三块结构，但重新整理层级：
1. 顶部身份区：骑手姓名、状态、说明
2. 中部活跃区：
   - 待接单池
   - 我的配送
3. 底部历史区：已完成历史

### 卡片信息层级
每张活跃卡片统一为 6 层：
1. 顶部：店铺名 + 状态标签 + 时间
2. 地址
3. 电话
4. 商品摘要
5. 金额 + ETA / 预约送达
6. 动作区

### 按钮层级
- 主按钮：高强调色，只保留一个主动作
- 次按钮：低强调，用于拒单 / 联系 / 导航
- 同一卡片不出现两个高优先级主动作抢注意力

这意味着：
- 待接单卡片主按钮是 `接单`
- 配送中卡片主按钮是 `送餐完成`
- `暂不接单` 是次按钮，不和主操作竞争

## 拒单反馈规则
### 业务语义
“暂不接单”不结束订单，也不把订单打成 cancelled；它只表示“当前骑手不接这单”。

### 持久化
沿用现有 `dispatch_meta` 备注链路：
- 记录最近一次骑手决定 `lastRiderDecision`
- 维护 `declinedRiderIds`

### 展示
- admin 可以显示“骑手反馈：某骑手已拒单 时间”
- rider dashboard 如需提示，只显示弱提示，不抢主流程
- Telegram 拒单成功后只需要给当前骑手明确反馈，不需要把消息流做得很复杂

## 关键风险与处理
### 1. 重复点击 / 旧按钮点击
处理方式：
- 以后端状态检查为准
- 双端收到状态不匹配时给出简短提示并刷新
- 不靠前端假设成功

### 2. Telegram 与 rider dashboard 展示不一致
处理方式：
- 将动作显示规则和状态文案映射收口到共享逻辑
- 双端只消费共享规则，不各自硬编码一套

### 3. UI 美化时顺手破坏现有订单操作
处理方式：
- 本轮只重排 rider 卡片结构和按钮样式
- 不改无关 API，不改非 rider 活跃流程
- 先补聚焦测试锁定按钮显示规则，再改页面

### 4. 拒单信息喧宾夺主
处理方式：
- 拒单反馈只作为辅助行或弱提示
- 主状态仍是 `待骑手接单 / 配送中 / 已完成`

## 验收标准
### 功能验收
1. Telegram 收到派单消息时，看到：
   - 接单
   - 暂不接单
2. Telegram 接单成功后，会收到新的配送消息，看到：
   - 送餐完成
3. rider dashboard 的待接单卡片显示：
   - 接单
   - 暂不接单
4. rider dashboard 的我的配送卡片显示：
   - 送餐完成
   - 联系客户
   - 导航
5. 完成配送后订单进入 `completed`

### 一致性验收
1. `awaiting_courier` 文案统一为 `待骑手接单`
2. `delivering` 文案统一为 `配送中`
3. `completed` 文案统一为 `已完成`
4. admin、rider、Telegram 不再混用“待骑手确认 / 骑手已接单”等旧文案

### 体验验收
1. 骑手看到界面后无需培训即可理解当前该点哪个按钮
2. 活跃卡片信息层级明显优于当前版本
3. 主按钮与次按钮不混乱、不抢视觉

## 测试策略
本轮实施必须采用 TDD，至少覆盖：

1. `rider dashboard` 在 `awaiting_courier` 显示“接单 + 暂不接单”
2. `rider dashboard` 在 `delivering` 显示“送餐完成”
3. Telegram 派单消息包含“接单 + 暂不接单”
4. Telegram 接单成功后触发新的“送餐完成”消息构建
5. 完成动作将订单从 `delivering` 推进到 `completed`
6. 统一文案映射在 admin / rider 相关入口保持一致
7. 拒单反馈仍被正确保留，不破坏当前 `dispatch_meta` 持久化

## 最终结论
本轮设计采用以下决策：
- 双端都支持：接单、暂不接单、送餐完成
- 双端都基于同一状态机：`awaiting_courier -> delivering -> completed`
- Telegram 使用“两阶段消息”而不是强依赖编辑旧消息按钮
- rider dashboard 采用简洁商务风重排
- 派单文案统一为：待骑手接单 / 配送中 / 已完成
- 拒单反馈保留为辅助说明，不升级为独立业务状态
