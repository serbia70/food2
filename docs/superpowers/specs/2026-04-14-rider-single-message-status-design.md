# Rider Single-Message Status Design

> 状态说明（部分过期）：这份设计记录的是 rider 单消息收口时的目标与约束；文中关于“发送第二条阶段消息”的描述属于当时的问题背景或历史兜底，不应再被当作当前主路径实现。

**Goal:** 让 Telegram 与 rider 客户端围绕同一套“状态词 / 动作词 / 时间记录”工作：Telegram 对每个订单始终只保留一条可编辑消息，rider dashboard 对每个订单始终只保留一张同步卡片，并统一修正骑手端时间为贝尔格莱德时区。

**Why now:** 当时 Telegram 在接单、取餐、送达时会发送第二条阶段消息，多单并行配送时容易把多条消息混在一起误点；同时 rider dashboard 直接截取 `createdAt` 字符串显示，未按 `Europe/Belgrade` 格式化，导致时间感知不稳定。

**Non-goals:**
- 不改后端主状态机，继续沿用 `awaiting_courier -> delivering -> picked_up -> completed`
- 不新增第二套 rider action API
- 不引入 Telegram 多层菜单、会话页或汇总页跳转
- 不把时间先提升为新的顶层业务字段，优先复用现有 `dispatch_meta`

---

## 1. 用户体验目标

### Telegram
- 每个订单在骑手私聊里只保留 **一条** 主消息
- 这条消息在每次动作后直接 **编辑原消息**，而不是补发阶段消息
- 按钮只显示当前下一步动作，避免歧义：
  - `接单`
  - `暂不接单`
  - `取餐`
  - `送达`
- 状态词与动作词严格分离：
  - `待接单`
  - `待取餐`
  - `配送中`
  - `已送达`
- 关键动作时间显示在正文里：
  - `接单时间`
  - `取餐时间`
  - `送达时间`

### Rider dashboard
- 每个订单只保留一张卡片
- 卡片标题、状态文案、动作按钮与 Telegram 完全一致
- 时间统一显示为贝尔格莱德时间
- 多单时仅通过卡片列表查看，不引入额外跳页或多层入口

---

## 2. 统一状态模型

继续使用当前业务状态：

| 业务状态 | 面向骑手的状态文案 | 动作按钮 |
| --- | --- | --- |
| `awaiting_courier` | `待接单` | `接单` / `暂不接单` |
| `delivering` 且未取餐 | `待取餐` | `取餐` |
| `picked_up` | `配送中` | `送达` |
| `completed` | `已送达` | 无 |

### 关键原则
1. **状态词只表达现在是什么**，不承担动作含义
2. **按钮只表达下一步要做什么**，不用“已取餐 / 已送达”这类容易误解的完成态词汇
3. Telegram 与 rider dashboard 共享同一套状态解析 helper，不能各自写分叉逻辑

---

## 3. 时间模型

### 显示时区
- 所有骑手可见时间统一按 `Europe/Belgrade` 格式化
- Telegram 与 rider dashboard 统一显示 `HH:mm`
- rider dashboard 当前 `src/pages/rider/dashboard.astro` 里对 `createdAt` 的字符串切片逻辑需要移除，改成正式格式化

### 记录内容
在 `dispatch_meta` 中维护动作时间：
- `acceptedAt`
- `pickedUpAt`
- `completedAt`

### 原因
- 这三个时间直接服务于骑手侧展示，不需要先上升为后端顶层字段
- 继续与现有 `dispatch_meta`、`remarksJson` 读写路径保持一致，改动范围小
- 如果后续需要报表，再考虑是否正式提炼为顶层字段

---

## 4. Telegram 单消息架构

### 核心设计
为每个订单绑定一个 Telegram 消息引用：
- 首次向骑手发送订单时，记录该消息的 `chat_id + message_id`
- 后续 `接单 / 取餐 / 送达` 都基于这对引用调用 Telegram edit message 接口
- 编辑成功后，消息正文和 inline keyboard 一起更新

### 单消息内容结构
建议正文固定为短结构：

```text
#A476 · 店铺A
状态：待取餐
接单时间：12:03

地址：...
电话：...
店铺地图：...
客户导航：...
```

### 按阶段更新规则
- `awaiting_courier`
  - 状态：`待接单`
  - 按钮：`接单`、`暂不接单`
- `delivering` 且未取餐
  - 状态：`待取餐`
  - 按钮：`取餐`
  - 显示：`接单时间`
- `picked_up`
  - 状态：`配送中`
  - 按钮：`送达`
  - 显示：`接单时间`、`取餐时间`
- `completed`
  - 状态：`已送达`
  - 按钮移除
  - 显示：`接单时间`、`取餐时间`、`送达时间`

### 拒单处理
- `暂不接单` 仍沿用当前拒单 / 续派语义
- 原消息应同步进入只读态，避免骑手在旧消息上继续操作
- 如果订单被改派给其他骑手，旧消息也要被编辑成“已失效 / 已改派”的只读状态

---

## 5. Rider dashboard 同步架构

### 展示层
rider dashboard 使用与 Telegram 相同的共享 helper 输出：
- 状态文案
- 当前可执行动作
- 应显示的动作时间
- 店铺名 / 店铺地图 / 客户导航等信息

### 交互层
rider dashboard 按同样规则只展示下一步动作：
- `接单 / 暂不接单`
- `取餐`
- `送达`

### 同步原则
- Telegram 点击动作后，dashboard 刷新应立即看到同样的状态和时间
- dashboard 点击动作后，Telegram 原消息也应反映同样的状态和时间
- 也就是说：**双端共享一套服务端事实来源，只是展示载体不同**

---

## 6. 服务端事实来源

保持当前“一个服务端 action 判定真相”的方向：
- 状态是否合法
- 当前骑手是否有权操作该订单
- 该写入哪个状态
- 该写入哪些 `dispatch_meta` 时间字段
- 该显示哪个动作按钮和状态文案

### 需要扩展的事实
除了现有状态判定，还要让共享 helper 能输出：
- `statusLabel`
- `primaryAction`
- `secondaryAction`（仅待接单时的 `暂不接单`）
- `acceptedAt`
- `pickedUpAt`
- `completedAt`
- `telegramMessageRef`（用于编辑原消息）

这样 Telegram 和 rider dashboard 都只消费 helper 结果，而不是自己拼语义。

---

## 7. 多单防错设计

为了让骑手同时配送多家时不混乱：

### Telegram
- 每单只有一条主消息
- 消息第一行固定包含：`订单号 + 店铺名`
- 状态单独一行
- 按钮只有一个当前动作，不同时出现多个阶段按钮

### Rider dashboard
- 每张卡片头部固定包含：`订单号 + 店铺名 + 状态`
- 时间显示紧跟状态区，不埋在正文里
- 动作按钮区域只出现当前阶段相关按钮

### 不做的事
- 不做“点击进入子页面再操作”
- 不做 Telegram 汇总菜单
- 不让一个订单在同一时刻出现 `取餐` 和 `送达` 两种阶段动作

---

## 8. 错误处理与兜底

### Telegram 编辑失败
若编辑原消息失败：
1. 订单状态更新仍应以服务端写入结果为准
2. 记录编辑失败原因，便于排查
3. 原则上不立刻回退为“发送第二条阶段消息（历史方案）”常态逻辑，避免重新引入消息洪泛
4. 仅在极端情况下保留明确的人工恢复路径，而不是自动分叉成第二套消息模式

### 历史旧消息
上线后，可能仍有旧结构消息残留：
- 新流程只保证新产生和可追踪的消息使用单消息编辑模式
- 对没有 message ref 的旧消息，不强行做复杂迁移
- 旧消息只作为过渡遗留，不作为长期语义依赖

---

## 9. 测试策略

### 单元 / spec
需要锁定：
- 状态文案与动作文案映射
- `dispatch_meta` 时间字段读写
- Telegram 文本构建
- Telegram inline keyboard 在不同阶段只出现正确动作
- rider dashboard 与 Telegram 共用同一套状态 helper

### 路由 / 集成
需要锁定：
- 接单后写入 `acceptedAt` 并编辑原消息
- 取餐后写入 `pickedUpAt` 并编辑原消息
- 送达后写入 `completedAt` 并编辑原消息
- 拒单 / 改派后旧消息变为失效只读态
- 编辑失败时不篡改业务状态

### 页面源码 / UI 合约
需要锁定：
- rider dashboard 不再手切时间字符串
- rider dashboard 只出现 `接单 / 暂不接单 / 取餐 / 送达`
- 不再出现把动作写成 `已取餐 / 已送达` 的新按钮文案

---

## 10. 实施顺序建议

建议拆成两个紧密相关但可控的子阶段：

### 阶段 1：统一语义与时间
- rider dashboard 改为贝尔格莱德时间
- 双端统一状态词 / 动作词
- `dispatch_meta` 增加动作时间记录
- rider dashboard 先消费新语义

### 阶段 2：Telegram 单消息编辑
- 首条消息记录 message ref
- 接单 / 取餐 / 送达改为 edit message
- 移除补发阶段消息主路径
- 补齐拒单 / 改派时的旧消息失效处理

这样做可以先收敛词义和时间，再收敛 Telegram 消息模型，风险更低。

---

## 11. 成功标准

1. rider dashboard 时间显示与贝尔格莱德一致
2. Telegram 不再因 `取餐` / `送达` 产生新消息
3. 一个订单在 Telegram 中始终只保留一条主消息
4. Telegram 与 rider dashboard 的状态词、动作词、关键时间一致
5. 多单同时配送时，骑手能仅凭消息头部和按钮快速区分订单
6. 旧的“已取餐按钮其实表示还未取餐”这类歧义被彻底消除
